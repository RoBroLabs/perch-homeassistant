# Perch companion protocol, version 1

The wire contract between the Perch tvOS app and its Home Assistant companion. It is language neutral. Both repositories copy this directory unchanged; neither edits its copy. A change is made once, here, and copied to the other side.

Contents: `schema/perch.schema.json` (JSON Schema 2020-12, one `$defs` entry per message, `additionalProperties: false` on every object), `fixtures/` (bare messages, mapped to schema entries in `fixtures/index.json` as `[{"file": "commands/manifest.result.json", "def": "ManifestResultFrame"}]`), `vectors/crypto.json` (fixed crypto inputs and outputs, generated by CryptoKit with `scripts/make-protocol-vectors.swift`), `words.json` (the 1296-word fingerprint list).

## Versioning

The protocol number is `1` and appears as `protocol` in the pairing request and in the `auth_required` and `auth` frames. Additive fields are allowed within a number: a reader ignores fields it does not know, a writer never depends on them. Anything else (removing or renaming a field, changing a meaning, a new required field, a new crypto step) bumps the number. A companion that gets a different number answers `unsupported_protocol` (pairing) or `auth_invalid` (WebSocket).

## Encoding

- Binary in JSON: standard base64 with padding. In `vectors/crypto.json`: lowercase hex.
- Times: ISO 8601 UTC with `Z`, for example `2026-11-15T20:30:00Z`. Days: `YYYY-MM-DD`.
- Ids are opaque strings; the app never parses them.
- URLs returned by the companion are paths beginning with `/`. The TV joins them to its base URL.
- Messages are JSON text frames or bodies, UTF-8.

## Crypto

Keys are X25519 and raw 32 bytes. The pairing nonce is 16 bytes. The code is 6 ASCII digits. `||` is concatenation.

- Binding: `HMAC-SHA256(key = code ASCII, msg = "perch-bind-v1" || tvPub || nonce)`.
- Fingerprint: `d = SHA-256("perch-fp-v1" || tvPub)`; for i in 0..3 take `words[uint16_be(d[2i..2i+2]) % 1296]`; join the four words with single spaces. Both sides show it so the admin can compare.
- Credential: 32 random bytes made by the companion. It stores only its SHA-256 as lowercase hex.
- Credential envelope (companion to TV, in the approved status): fresh ephemeral X25519 key `eph`; `shared = X25519(eph, tvPub)`; `key = HKDF-SHA256(ikm = shared, salt = pairing nonce, info = "perch-cred-v1" || ephPub || tvPub, L = 32)`; ChaCha20-Poly1305 with a 12-byte nonce and AAD = tvPub. Wire: `ephPub(32) || nonce(12) || ciphertext || tag(16)`.
- Auth proof (TV to companion), v2: the companion sends `challenge` (32 bytes) and `server_key` (a fresh ephemeral X25519 public key per connection). The stored value is `SHA-256` of the raw 32 credential bytes; the companion keeps it as lowercase hex, and the 32 raw digest bytes are what go into the key derivation. The TV computes `shared = X25519(tvPriv, serverKey)`; `ikm = shared || SHA-256(credential)` (64 bytes); `key = HKDF-SHA256(ikm, salt = challenge, info = "perch-auth-v2" || serverKey || tvPub, 32)`; ChaCha20-Poly1305 with AAD = challenge and plaintext = credential. Wire: `nonce(12) || ciphertext || tag(16)`. The credential never crosses the wire in clear. The companion derives the same key from its ephemeral private key, the stored TV public key and its stored hash (decoded from hex to 32 raw bytes), opens the proof, hashes the result and compares it with the stored hash in constant time. Why the hash is mixed in: `server_key` is not authenticated, so without it a host on the LAN pretending to be the companion could open the proof and read the credential; without the stored hash it cannot.

`vectors/crypto.json` holds fixed inputs and outputs for every step (public test values only). Both implementations must reproduce them. Fixture binary fields are the real vector values.

## Pairing (HTTP, local only, no Home Assistant authentication)

The companion refuses any pairing request that arrives over Home Assistant Cloud with 403 `pairing_local_only`, even when the cloud switch is on, and any non-local peer with 403 `not_local`.

- `POST /api/perch/pair`, body `PairStartRequest {protocol: 1, tv_name (1..64 characters), public_key, nonce, hmac}`. Reply 200 `PairStartResponse {pairing_id, expires_in}`, where `expires_in` is the seconds left in the pairing window (1 to 300; less than 300 when a TV joins a window that is already open). The TV counts down from the value it is given.
- `GET /api/perch/pair/{pairing_id}`. Reply 200 `PairStatusResponse`, exactly one of:
  - `{status: "pending"}`
  - `{status: "approved", tv_id, envelope}`
  - `{status: "rejected"}`: the admin chose "They do not match".
  - `{status: "cancelled"}`: attempts used up, or a second key verified the same code.
  - `{status: "expired"}`
- The companion chooses `tv_id` and returns it on approval.
- Errors, body `PairError {error, retry_after?}`: 400 `bad_request`, 404 `not_found`, 409 `busy`, 429 `rate_limited` (with `retry_after` in seconds), 403 `not_local`, 403 `pairing_local_only`, 400 `unsupported_protocol`.

## WebSocket `GET /api/perch/ws`

The companion's own endpoint, not Home Assistant's `/api/websocket`. No Home Assistant user or token is involved. Frames are JSON text in the Home Assistant style.

1. Server sends `AuthRequiredFrame {type: "auth_required", protocol: 1, challenge, server_key}`.
2. Within 10 seconds the TV sends `AuthFrame {type: "auth", protocol: 1, tv_id, proof}`. Here `tv_id` is only the lookup handle for which stored key and hash to check. After a valid proof the connection is bound to that TV.
3. Server sends `AuthOkFrame {type: "auth_ok", protocol: 1, companion_version}`, or `AuthInvalidFrame {type: "auth_invalid"}` and closes with 4001. Any non-auth frame before auth also gets `auth_invalid` and close 4001.
4. `RevokedFrame {type: "revoked"}` then close 4003: the TV was removed in Home Assistant, or after `perch/unpair`.
5. `PingFrame {id, type: "ping"}` is answered by `PongFrame {id, type: "pong"}`.

Scope (which TV, which room, which lights, which cameras) is always taken from the bound connection. Command frames never carry `tv_id`; the schema forbids it. A companion ignores any such field and never uses a frame field for scope.

### Commands

`{id, type: "perch/<name>", ...fields}`. `id` is a positive integer, increasing per connection. The reply is a `ResultFrame` with the same `id`:

- success: `{id, type: "result", success: true, result: {...}}`
- failure: `{id, type: "result", success: false, error: {code, message}}`

Error codes: `not_allowed`, `not_found`, `invalid_format`, `refused_for_role`, `rate_limited`, `unavailable`, `unknown_command`, `not_supported_yet`. Messages are plain words for logs and are never shown verbatim to users.

| Command | Request fields | Result |
|---|---|---|
| `perch/manifest` | none | `{tv_id, tv_name, room: {id, name} or null, rooms: [{id, name}] (includes the TV's room; `room` is null until the admin picks the TV's room in Home Assistant, and then `rooms` is empty), lights: [{id, name, room_id, dimmable}], cameras: [{id, name, room_id or null}], doorbell: {camera_id or null} or null, scenes: [{id, name, purpose: "movie_night" / "paused" / null}], let_in_available, notify_available?}` |
| `perch/states` | none | `{lights: [{id, on, brightness 0..100 or null, available}]}` |
| `perch/subscribe` | `{topics}`: 1 to 4 unique of `doorbell`, `events`, `states`, `manifest` | `{topics}` |
| `perch/camera` | `{camera_id, kind: "snapshot" / "stream"}` | `{url, expires_at}` |
| `perch/playback` | `{state: "playing" / "paused" / "stopped", media: "film" / "episode" / "music" / "other", lighting}` | `{applied, reason: null / "lighting_off" / "not_after_sunset" / "skipped_tonight" / "no_room"}` |
| `perch/light` | `{light_id, on?, brightness? 0..100}`, at least one of `on` and `brightness` | `{}` |
| `perch/scene` | `{scene_id}` | `{}` |
| `perch/events` | `{day, camera_id?, role: "adult" / "teen" / "kid"}` | `{events: [EventItem]}`; a kid gets error `refused_for_role` |
| `perch/skip_tonight` | `{until}` | `{}` |
| `perch/unpair` | none | `{}`, then `revoked` and close 4003 |
| `perch/let_in` | `{sealed_pin}` | `{opened, refusal: null / "no_ring" / "wrong_pin" / "locked_out" / "not_allowed"}` |
| `perch/notify` | `{kind: "request_ready", title_id, title_name?}` | `{sent, refusal: null / "not_set_up" / "already_sent" / "rate_limited"}` |

`perch/notify` (companion 0.2.0) asks the companion to tell the household's phones something. The TV picks a fixed `kind` and never names a service or supplies wording. `request_ready`: a title the household asked for is ready to watch. The companion sends "Your request is ready to watch", or "<title_name> is ready to watch" only when the admin allows names (they show on a locked phone). `title_id` (1 to 128 of `A-Z a-z 0-9 . _ : / -`) is used only to tell each title once, across all TVs and restarts; the companion keeps only its hash. `title_name` is 1 to 200 characters; control and markup characters are dropped and at most 100 are kept. Refusals: `not_set_up` (no phone picked or the switch is off), `already_sent`, `rate_limited` (10 an hour per TV, 30 an hour in all). If no phone takes the message within 10 seconds the reply is error `unavailable`, and the title may be tried again. `notify_available` in the manifest is true when a request notice would be sent; a companion before 0.2.0 leaves it out, which means false.

`EventItem {id, camera_id, label, started_at, ended_at or null, snapshot_url, clip_url or null, expires_at}`.

`perch/let_in` is RESERVED for 1.5.0 (`"x-reserved": "1.5.0"` in the schema). `sealed_pin` is base64, sealed with a key the 1.5.0 schema will define. Until then the companion answers error `not_supported_yet`. There is no `perch/doorbell` command; the doorbell is only the `doorbell` topic.

### Events

After `perch/subscribe`, pushes arrive as `EventFrame {id, type: "event", event: {topic, data}}`, where `id` is the id of the subscribe command.

| Topic | `data` |
|---|---|
| `doorbell` | `{camera_id or null, rang_at}` |
| `states` | `{lights: [light states that changed]}` |
| `manifest` | `{}` (the TV refetches `perch/manifest`) |
| `events` | `{event: EventItem}` |
